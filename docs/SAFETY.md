# Rind 的安全模型

[English](en/SAFETY.md) | 中文

这是一个会移动你文件的工具，所以它把「凭什么敢动」写在这里。想上报漏洞请看 [SECURITY.md](../SECURITY.md)。

## 1. 承诺

**Rind 从不直接删除任何东西。** 所有移动都走 `NSFileManager.trashItem`，进废纸篓；每一次移动都记进 History，
记录它在废纸篓里的实际位置，可以逐项放回。真正不可逆的只有一件事：你清空废纸篓——那是你自己在 Finder 里做的，
Rind 不代劳。它也需要你主动点击才会动手（没有任何自动清理、没有常驻进程）。

## 2. 唯一出口

卸载、孤儿、清理、空间、启动项、`rind trash`——所有会移动东西的功能都汇到同一个函数
`rind_core::remove::trash_items`。它按固定顺序做六件事：

1. **解析真实路径**：把选中项解析成盘上的真实位置（解掉祖先里的符号链接、还原实际大小写）。
2. **查保护区**：路径本身、它的祖先、以及目录里往下 6 层的媒体库 / 钱包 profile。
3. **拒绝外层**：外层目录里只要有不能动的项（受保护 / macOS 自己的 / 要管理员 / 在用），整个外层拒绝。
4. **先记意图**：把「我要移走这个」写进 History（`history.jsonl`）；写不进去就一个文件都不动。
5. **移动**：一个文件一次 `trashItem`，同时核对搬走的是不是查过的那个对象（设备号 + inode）。
6. **回填**：把它在废纸篓里的实际位置写回记录；写不回去就停下，不再动后面的事，并如实报告已经发生的部分。

任何要移动文件的新功能都得走这里——这是代码审查里最不愿意破例的一条。

## 3. 保护区

保护区里的东西**任何选项、任何参数、任何 `--all` 都不能覆盖**：

iCloud Drive / CloudStorage、钥匙串、`~/.ssh`、GPG 密钥、Mail、Messages、Safari 与其 Cookies、
通讯录、照片库与音乐库（`*.photoslibrary` / `*.musiclibrary` 等后缀，不论放在哪）、iPhone / iPad 备份、
桌面 / 文稿 / 下载等用户文件夹本身、系统路径（`/System`、`/usr`、`/bin`……）、
带加密钱包扩展的浏览器 profile（MetaMask 等）。

判定方式是**按盘上的真实身份**，不是比字符串：大小写变体（APFS 默认大小写不敏感）、中间夹着符号链接、
`..` 穿插，都会先解析成真实路径再判定。`rind protected` 列出全部规则。

## 4. History 与放回

- 记录写在 `~/Library/Application Support/Rind/history.jsonl`，一行一条；同一批移动共用一条记录。
- 放回时逐项校验：它确实在废纸篓里、原路径是干净的绝对路径、解析后仍等于当初记录的位置、不在保护区。
  任何一条不满足就跳过这一项并说明原因，其余照常放回。
- 放回是「不覆盖已有文件」的语义（`RENAME_EXCL`）：原处已经有东西时不会盖掉它。
- 跨卷放回（比如外置盘）会先复制、核对文件数与字节数，再删掉废纸篓里那份。

## 5. 启动项为什么更麻烦

启动项要动的是 `launchctl`，而它读的是磁盘上的 plist——「检查」和「动手」之间存在时间差。Rind 的处理是：

- 只看不收符号链接：`~/Library/LaunchAgents` 本身或它到家目录之间哪一级是符号链接，整个用户域都不列。
- 动手前用 `O_NOFOLLOW` 重新打开 plist 核对：普通文件、属于当前用户、组和其他人写不了、不超过 1 MB、
  不是深嵌套的炸弹（与 Info.plist 共用同一套 tame 检查）、盘上的 `Label` 与扫描时逐字相同、程序也没换。
- 记下这份文件的身份（设备 + inode + 大小 + mtime / ctime + 内容哈希），在 `bootout` 之前、`bootout` 之后、
  以及真正 `rename` 之前各比一次；任何一次不符就不移动，并把已经卸下来的重新 `bootstrap` 装回去。
- label 只认 `[A-Za-z0-9._-]`；`/Library` 下和 `com.apple.*` 的项不操作。

## 6. 已知边界（写明的取舍）

这些不是「以后再说」，而是有意划定的边界：

| 边界 | 说明 |
| --- | --- |
| 目录深层探测 | 移动一个目录前会往下看 6 层、最多 20 万个条目；更深处的媒体库 / 钱包不会被拦。这是「能拦住绝大多数，又不至于让清理没法用」的折中。 |
| 裸符号链接 | 移走一个指向保护区的**链接**本身是允许的——链接不是目标，移走它不会带走它指向的东西，History 也能把它放回来。 |
| launchctl 的瞬间 | 最后一次核对与 `launchctl` 自己读文件之间仍有极短窗口，这是它的接口决定的。 |
| 需要管理员权限 | `/Library` 下、系统域的启动项等只列出、不搬运，Rind 不申请提权。 |
| 完全磁盘访问 | 没授权时沙盒容器等位置读不了，会标「读不了」，不会显示成 0 字节。 |
| `--all` | 会把「可能 / 共用 / 读不了」的也带上，但它仍然越不过保护区。 |
| 清空废纸篓 | 空间只有在清空废纸篓后才真正回来；在那之前一切都能放回。 |

## 7. 怎么自己验证

不想读代码的话，这样看：

```sh
rind protected                    # 它保证不动哪些地方
rind leftovers 微信                # 看它凭什么认为这些文件属于微信
rind uninstall 微信 --dry-run      # 预演：会移走什么、拒绝什么、释放多少
rind orphans --trash --dry-run     # 同上，孤儿残留
rind clean --trash --dry-run
rind history --json                # 它到底做过什么
```

预演和真跑给的判断是同一份。想更硬核一点：每一条安全检查都有对应的测试
（`cargo test -p rind-core`，213 个），其中包括刻意构造的攻击用例——符号链接换向、同名同构目录替换、
原地改写文件并把时间戳设回去、深嵌套 plist 炸弹。测试从不调用真实的 `launchctl`，也不碰你的真实文件：
它们在自己的临时环境里跑。
